# 06 数据库基础

这篇以 PostgreSQL 为例。MySQL 大同小异，语法差一点点。目标是让你能自己建表、
查数据、看懂慢查询，不是让你成为 DBA。

## 1. 连上去

```bash
psql -h 127.0.0.1 -U postgres -d mydb
# 或者容器里
docker exec -it mydb psql -U postgres -d mydb
```

常用元命令（`\` 开头的，只在 psql 里有效）：

```
\l           列出所有数据库
\c mydb      切换数据库
\dt          列出所有表
\d 表名      看表结构
\d+ 表名     看表结构 + 索引 + 大小
\x           切换成竖排显示（列多的时候好用）
\q           退出
```

`\x` 那个我很常用。表字段一多，横着显示会被截断，竖排看得清楚。

## 2. 建表

```sql
CREATE TABLE users (
    id          BIGSERIAL PRIMARY KEY,
    email       TEXT NOT NULL UNIQUE,
    name        TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES users(id),
    amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0),
    status      TEXT NOT NULL DEFAULT 'pending',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

几个我坚持的写法：

- **金额用整数分，不用浮点。** `0.1 + 0.2 != 0.3` 在浮点里是真的，钱上不能这么玩。
- **时间用 `TIMESTAMPTZ`，不用 `TIMESTAMP`。** 带时区，省得跨时区一团乱。
- **`BIGSERIAL` 不用 `SERIAL`。** SERIAL 是 32 位，21 亿就溢出了，很多业务到不了
  但也不是没可能。用 BIGINT 没坏处。
- **加 `CHECK` 约束。** 数据库层面拦一道，比应用层可靠。

## 3. 查询

```sql
-- 基本
SELECT id, email, name FROM users WHERE created_at > '2026-01-01';

-- 排序 + 分页。注意 OFFSET 大了很慢，见下面索引那节
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100;

-- 聚合
SELECT status, COUNT(*), SUM(amount_cents) / 100.0 AS total_yuan
FROM orders
GROUP BY status
HAVING COUNT(*) > 10;

-- JOIN
SELECT u.email, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.email
ORDER BY order_count DESC
LIMIT 10;
```

**`LEFT JOIN` 和 `INNER JOIN` 的区别**新手经常搞混：`INNER JOIN` 只返回两边都
匹配的行，`LEFT JOIN` 保留左表所有行，右表没匹配的补 NULL。上面这个例子要
`LEFT JOIN`，否则没下过单的用户就不会出现。

**`GROUP BY` 的坑**：`SELECT` 里除了聚合函数外的字段，都必须出现在 `GROUP BY`
里。上面的例子里我 `GROUP BY u.id, u.email` 两个都写了，因为 PostgreSQL 要求
这样（MySQL 有时会放你一马，但那是错的）。

## 4. 索引

索引让查询变快，代价是插入变慢、占空间。加在**经常出现在 WHERE、JOIN、ORDER BY
里的字段**上。

```sql
CREATE INDEX idx_orders_user_id ON orders (user_id);
CREATE INDEX idx_orders_created_at ON orders (created_at DESC);
```

**复合索引的顺序很重要**：

```sql
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
```

这个索引能加速 `WHERE user_id = 1` 和 `WHERE user_id = 1 AND status = 'paid'`，
但**不能**加速 `WHERE status = 'paid'`。规则是"最左前缀"。记不住的话就想：
索引像电话簿按姓+名排序，你能快速找"姓张的"，但找不了"所有叫伟的"。

**怎么知道查询用没用索引**：

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42;
```

看输出里是 `Seq Scan`（全表扫，慢）还是 `Index Scan`（走索引，快）。
`Seq Scan` 在数据量小的时候反而是对的，别看到就慌。

## 5. 事务

要么全成功，要么全失败。转账是经典例子：

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

中间任何一步出错就 `ROLLBACK`。**注意**：`BEGIN` 之后不 `COMMIT` 也不
`ROLLBACK` 就关连接，事务会挂在那里占着锁，别人就卡住了。我在测试环境制造过
一次死锁，就是因为忘了 commit。

## 6. 慢查询排查

PostgreSQL 可以开慢查询日志：

```sql
-- 记录超过 1 秒的查询
ALTER SYSTEM SET log_min_duration_statement = 1000;
SELECT pg_reload_conf();
```

看正在跑的查询：

```sql
SELECT pid, now() - query_start AS duration, query
FROM pg_stat_activity
WHERE state = 'active' AND query_start < now() - interval '5 seconds'
ORDER BY duration DESC;
```

发现有卡了很久的，可以 `SELECT pg_cancel_backend(pid)` 取消它。

## 7. 几个我踩过的坑

- **`UPDATE` 忘了 `WHERE`**：整表被改。在事务里做，`UPDATE` 前先
  `SELECT COUNT(*)` 看看影响多少行。psql 里可以设
  `\set AUTOCOMMIT off` 强制手动提交。
- **`NULL` 的比较**：`WHERE name != 'x'` 不会返回 `name IS NULL` 的行。
  NULL 参与的任何比较都是 NULL，不是 true。要写 `WHERE name != 'x' OR name IS NULL`。
- **连接数爆了**：报 `FATAL: sorry, too many clients already`。应用里要用
  连接池，别每次请求新建连接。
- **字符串拼 SQL**：`"SELECT * FROM users WHERE name = '" + name + "'"` 是
  SQL 注入。永远用参数化查询 `WHERE name = %s`（Python 里传参数）。
