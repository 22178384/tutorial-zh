# 07 调试技巧

写代码一半时间在调试。这篇讲我怎么定位问题，尤其是那种"昨天还好好的，今天就
不对了"的情况。

## 0. 心法：先想再敲

新手最常犯的错是看到问题就瞎改，改一行跑一次。这样效率极低。

正确顺序：

1. **复现**。能稳定复现吗？不能的话先想办法复现，别急着改。
2. **缩小范围**。问题在哪一层？前端、后端、数据库、网络？
3. **提假设**。我猜是因为 X。然后**设计一个能验证 X 的实验**。
4. **验证**。跑实验，看假设对不对。不对就回第 3 步。

关键是第 3 步的"设计实验"。比如你猜是缓存问题，那就把缓存关了再跑一遍，
而不是盯着代码看。

## 1. 读堆栈

Python 的报错信息是从下往上读的。最后一行是错误类型和消息，往上找是"谁调用了谁"。

```
Traceback (most recent call last):
  File "app.py", line 42, in <module>
    main()
  File "app.py", line 30, in main
    process(data)
  File "app.py", line 18, in process
    return data["user"]["name"]
KeyError: 'user'
```

从下往上：`KeyError: 'user'` 是错误本身，`data["user"]` 是出错的那行，
`app.py:18` 是位置。**先看最后一行，再看你代码里最近的那个 `File` 行**。
标准库和第三方库的帧可以跳过，除非你怀疑是库的问题。

`KeyError: 'user'` 意思是 `data` 这个字典里没有 `'user'` 这个 key。八成是上游
返回的数据结构和你想的不一样。这时候别猜，`print(data)` 看看实际长什么样。

## 2. print 大法

别瞧不起 print，能解决 80% 的问题。但要有章法：

```python
# 不好：不知道是哪次循环、哪个变量的
print(data)

# 好：带上下文
print(f"[debug] 处理第 {i} 条, id={data.get('id')}, keys={list(data.keys())}")
```

`print` 完记得删掉。我习惯用 `logging.debug`，这样能通过日志级别控制，
不用满世界找 print。

## 3. 断点调试

`print` 不够用的时候上 pdb：

```python
import pdb; pdb.set_trace()
```

（Python 3.7+ 可以直接写 `breakpoint()`。）

程序跑到这里会停下来，进入交互。常用命令：

```
n (next)      执行下一行，不进入函数
s (step)      进入函数
c (continue)  继续运行到下一个断点
l (list)      显示当前位置附近的代码
p 变量名       打印变量（比 print 强，能打印对象内部）
pp 变量名      美化打印
w (where)     看当前调用栈
q (quit)      退出
```

我最常用的是 `p` 和 `w`。`w` 能看完整的调用链，搞不清"我怎么跑到这来的"时候很有用。

VS Code 里可以直接在行号左边点一下打断点，比 pdb 舒服，推荐。但服务器上没图形
界面的时候 pdb 是唯一选择。

## 4. 二分定位

当你不确定问题出在哪一步，用二分法砍。

场景：一个处理 1000 条数据的脚本，跑到第 400 条崩了。

```python
# 先确认是数据问题还是代码问题
data = load_data()
for i, item in enumerate(data):
    if i == 400:
        print(f"第 400 条: {item}")   # 看这条数据有什么特别
    process(item)
```

或者更直接：只跑前 500 条，能不能过；能过就说明问题在后 500 条，继续对半砍。

`git bisect` 是这套思路在 git 历史上的应用。不知道是哪个 commit 引入的 bug 时：

```bash
git bisect start
git bisect bad                 # 当前是坏的
git bisect good v1.2.0         # 这个版本是好的
# git 会自动 checkout 到中间某个 commit
# 你测试，然后告诉它
git bisect good   # 或 git bisect bad
# 重复几次，git 会告诉你第一个坏掉的 commit
git bisect reset
```

对于有测试的项目，`git bisect run pytest` 可以全自动，几分钟就定位到。

## 5. 看日志的正确姿势

线上问题只能靠日志。几条经验：

```bash
# 实时跟，但过滤掉噪音
tail -f app.log | grep -v "healthcheck"

# 找某个请求 ID 的完整链路
grep "req-abc123" app.log

# 看某个时间段
sed -n '/2026-09-22 14:00/,/2026-09-22 14:10/p' app.log
```

所以**日志里一定要带请求 ID**。用户报"我下单失败了"，你能靠 ID 把这次请求的
所有日志捞出来，而不是在几万行里瞎找。

**日志分级要用对**：

- ERROR：真出错了，需要人看
- WARNING：不太对但还能跑，比如重试了一次
- INFO：关键流程节点，比如"订单创建成功"
- DEBUG：调试细节，生产环境关掉

如果所有东西都打成 ERROR，那 ERROR 就等于噪音，没人会看。

## 6. 几个常见"诡异"问题

**"我明明改了代码怎么没生效"**

按顺序查：改的是不是正在跑的那份代码（`pwd`、`which`）？缓存（`__pycache__`、
浏览器、CDN）？改完有没有重启进程？改了配置文件有没有 reload？

**"本地好的，服务器不行"**

九成是环境差异：Python 版本、依赖版本、环境变量、文件权限、时区。
`pip freeze` 两边对一下，`env | sort` 两边对一下，很快能发现。

**"时好时坏"**

基本可以确定是并发问题或者时序问题。或者依赖了外部服务，外部服务偶尔抽风。
先看是不是只有高并发时出现。

**"重启就好了"**

说明有状态没清干净，或者有内存泄漏。重启只是掩盖问题，根因还在。这种 bug
最难查，但也最值得查，因为它一定会再犯。

## 7. 最后

调试能力比写代码能力更重要。写代码是在理想情况下的工作，调试是在信息不全、
时间紧张的情况下找真相。多练。

有问题先自己查，查不出来再问人。问的时候把"你做了什么、期望什么、实际是什么、
报错是什么、试过哪些方法"讲清楚。这样别人才帮得上你。
